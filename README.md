# 八字 · 开源排盘引擎

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)
![Python](https://img.shields.io/badge/python-3.9%2B-blue)
![Dependencies](https://img.shields.io/badge/dependencies-none-brightgreen)

一个只用 Python 标准库的八字排盘引擎，以及一份可以装进任何 AI 助手的 `SKILL.md`。

**它能做的是把出生时刻精确地变成一张八字盘。它不做的是告诉你命好不好。**

这不是偷懒 —— 是本项目的核心主张，理由写在 §2。

## 一、三十秒上手

不用装包，仓库里的 Python 直接跑：

```bash
# Markdown 报告（给人看，也给 LLM 看）
python scripts/bazi.py --date 1990-06-15 --time 12:30 --gender male --city 北京

# JSON（给程序看）
python scripts/bazi.py --date 1990-06-15 --time 12:30 --gender male --city 北京 --format json

# 排未来十五年流年
python scripts/bazi.py --date 1990-06-15 --time 12:30 --gender male \
    --city 上海 --liunian 2026-2040 -o report.md
```

Python 里调用：

```python
from bazi import BirthInput, build_chart, compute_dayun

chart = build_chart(BirthInput(1990, 6, 15, 12, 30, gender="male", longitude=116.4))
print(chart.pillars["day"].ganzhi)     # 辛亥
info, yun = compute_dayun(chart, 8)
print(info.summary, yun[0].ganzhi)
```

跑测试：

```bash
python -m unittest discover -s tests   # 排盘、规则候选、比较与输出回归
```

### 候选盘与传统结构（0.2.0）

```bash
# 时间不确定：按分钟比较，跨午夜范围也支持
python scripts/bazi.py --date 2000-01-01 --time-range 23:30-00:30 --city 北京 --format json

# 夏令时或交节精度有歧义：比较输入假设与节气敏感性
python scripts/bazi.py --date 1990-06-15 --time 14:30 --gender male --city 北京 --compare --format json
```

输出增加月令格局候选、条件、不满足项、反证线索、原文来源和未评估范围；
原局、大运及流年列六冲/六合/完整三合支组。它们是结构证据，不是成格、合化或用神结论。
主线与出处见 [references/patterns.md](references/patterns.md)，比较方式见
[references/uncertainty.md](references/uncertainty.md)。

JSON 模式会把未确认夏令时提示纳入 `告警`；大陆确认后才回拨。
海外请用 `--tz` 指定出生时实际偏移（含夏令时），`--dst-adjust` 不支持海外。
流年字段原“虚岁”更名为“年份差”，计算含义不变；客户端应同步字段名。
候选组保留全部输入情景与起运日期范围，代表盘日期不能替代整组范围。

## 二、为什么它不「算命」

市面上叫「AI 算命」的东西，绝大多数是让模型直接吐结论。那条路有个绕不过去的问题：
**模型的干支推算不可靠，而它自己不会承认。**

一个八字里，年柱看立春、月柱看节、日柱看儒略日、时柱看真太阳时 —— 四柱里
有三柱是由时刻决定的，而「立春当天凌晨出生的人该算哪一年」这种问题，
模型靠概率是猜不对的，猜错了还说得头头是道。

所以本项目的分工是：

| 谁来做 | 做什么 | 为什么 |
| --- | --- | --- |
| **本引擎** | 排盘：四柱、十神、藏干、纳音、长生、神煞、大运 | 确定性计算，同一输入永远同一输出，可复核 |
| **LLM（或你自己）** | 解读：把排盘结果组织成人话 | 需要语言、需要与两千年注疏传统对话 |

`SKILL.md` 就是给 LLM 看的说明书，规定它必须先用脚本排盘、再拿着 `references/`
里的象义文档说话，**不允许凭模型自身的命理知识补数据**。

一句话：**排盘的归排盘，解盘的归解盘。** 混在一起的产物既不可信也不可查。

## 三、零依赖是硬约束

`pyproject.toml` 的 `dependencies` 是空的，而且希望它一直是空的。

理由：

1. **命理工具要有几十年的寿命。** 用户手里 2020 年排的盘，2040 年还要能对上。
   依赖树里任何一个包弃坑、改 API、换协议，这件东西就坏了。
2. **可审计。** 一张表、一个公式看错了就是看错了，中间不隔着别人的实现。
3. **可嵌入。** 塞进 Skill、塞进小程序、塞进离线环境，都不用担心环境问题。

代价是自己要写天文算法。值得 —— 见下一节。

## 四、精度：拿权威数据测出来的数字

本节是所有使用者最该读的一节。

### 4.1 节气精度（实测，非估计）

本引擎用 Jean Meeus《天文算法》第 25 章的低精度太阳坐标公式求节气。
它好用、零依赖、任意年份可算，但有明确的精度上限。

**2026-10-05 的实测结果：**

| 校准源 | 说明 |
| --- | --- |
| 紫金山天文台《中国天文年历》 | 权威发布值 |
| `lunar-javascript` `getJieQiTable()` | 与上述同源口径，逐项差 8–16 秒；也是本次采样工具 |
| `pyephem` 4.2.1 | VSOP/ELP 量级高精度星历 |

样本：1900 / 1980 / 1990 / 2024 / 2050 五个年份的全部十二个「节」，共 60 个数据点。

> **结论：本引擎的节气时刻与权威值相差 −630 秒 ~ +223 秒，
> 最坏约 ±10.5 分钟，典型约 ±4 分钟。**

这个数字与 Meeus 公开的 0.01° 精度（对应时间约 15 分钟）完全吻合 ——
**是公式的固有误差，不是实现错误**。这一点单独验证过：本实现的太阳视黄经
与《天文算法》例 25.a 的标准答案逐位一致（差值 0.00000°）。

**四柱本身的对照**：随机生成 1940–2035 的 40 个日期与 lunar-javascript 对拍，
**40 / 40 完全一致**（年柱、月柱、日柱、时柱四项逐项比对）。这批期望值已固化为测试用例。

上述为既有实测记录；60 点原始节气样本及完整校准脚本尚未随仓库保存。
现有冻结四柱样本能检验四柱回归，不能独立复现这组节气误差统计。

### 4.2 这个误差意味着什么

每偏离 1 分钟的排盘结果就会出错的人，是那些出生在**交节时刻前后十几分钟内**的人。
估算一下：每年 12 个节 × 30 分钟窗口 ≈ **每一千四百个人里有一个**会被排错月柱或年柱。

频率不高，但对那个人来说整张盘都错了。所以本引擎的处理是：

**出生时刻落在某个节 ±15 分钟内时，输出会带一段明确告警**，而不是悄悄地给个错答案：

```
⚠️ 出生时刻距「立春」仅 3.7 分钟。本引擎节气精度约 ±10 分钟，
   月柱可能排错，请核对出生时间后再用。
```

### 4.3 如果需要更高精度

替换 `astro.sun_apparent_longitude` 一个函数即可（换成 VSOP87 完整项或 JPL DE 星历），
其余代码一行不动 —— 这是模块特意留的接缝。换完之后请用 §4.1 同样的流程复测，
并把新数字写回 `astro.py` 文件头。**欢迎这样的 PR。**

### 4.4 其他部分的精度

| 环节 | 精度 | 说明 |
| --- | --- | --- |
| 日柱、时柱的天干地支 | 精确 | 纯算术，不存在误差 |
| 真太阳时（经度项） | 精确 | 输入的经度有多准就有多准 |
| 均时差 | ±0.2 分钟 | NOAA 近似式 |
| ΔT | < ±1 秒 | IERS 标准值线性插值 |
| 起运日期 | 近似 | 依赖节气时刻，且流派本身就有 ±几天的口径差异 |

## 五、排盘口径：每个有分歧的地方都写在这里

命理界很多问题不是「对错」，是「流派」。本项目明知这些争议的存在，
于是把它们全部参数化，并把默认值记录下来。清单见 `references/decisions.md`，摘要：

### 5.1 年柱切换点

**默认值：以立春时刻**（不是农历正月初一，也不是公历一月一日）。

国家标准 GB/T 33661-2017 规定农历年的命名以正月初一为准，但八字使用的是
干支历，以立春为年首 —— 这是命理界的通行做法。两者要分清楚。

### 5.2 晚子时（23:00–00:00 出生）

自古有分歧，四家教法都支持：

| `--late-zishi` | 日柱 | 时柱天干 | 备注 |
| --- | --- | --- | --- |
| `next-day`（默认） | 次日 | 次日日干 | 最通行 |
| `current-day` | 当日 | 当日日干 | |
| `day-cur-time-next` | 当日 | 次日日干 | 俗称「夜子时」 |
| `all-current` | 当日 | 当日日干 | 连真太阳时跨日都不做 |

### 5.3 夏令时：只提示，不自动减 1 小时

1986–1991（以及更早的几个年代）中国大陆实行夏令时，钟表拨快 1 小时。
而时辰是 2 小时一档 —— **出生在时辰边界的人，命盘会整个换掉。**

即便如此，脚本检测到命中夏令时区间时**只在 stderr 打印提示**，不会自动回拨：

> 我们无法知道用户报的是夏令时读数、还是他自己已经换算过的标准时。
> 默默减一小时既可能算错，又会把所有存量历史命盘悄悄改掉。

需要回拨的用户请显式加 `--dst-adjust`，由使用者自己确认。
这条策略来自同为 MIT 协议的参考项目 ziwei-doushu 的同一决策，在此致谢。

### 5.4 真太阳时：要么做全套，要么一点都不做

```
地方真太阳时 = 钟表时间 − 时区偏移 + 经度/15 (小时) + 均时差
```

没有经度时（未传 `--city` / `--longitude`），**完全不做校正**。
半吊子校正比不校正更危险 —— 它给人「已经修正过了」的错觉。

经度的影响有多大？拉萨（东经 91.11）与东经 120 相差近 **2 小时**，
正好一个时辰。所以城市表做到了区县级：北京朝阳（116.49）与
辽宁朝阳（120.5）相差近 16 分钟，落在时辰边界附近就是两种命盘 ——
命令行遇到同名地点会直接报歧义让你选，不猜。

### 5.5 日主强弱：启发式，不是定式

命理界对身强弱至少有六七套互不支持的算法。本引擎给的是一套**加权启发式**，
它的价值不在于「算得准」，而在于**每一分都摊开写**：

```
月令得「死」：-28 分（火月，日主属金）
年柱天干十神「劫财」无根：+2.5 分
月柱天干十神「伤官」有根：-6.0 分
时柱天干十神「正财」有根：-7.0 分
→ 合计 -38.5 分，判为「身弱」
```

想改权重就改 `chart._MONTH_POWER_SCORE` 和 `chart._STEM_SUPPORT`。
**别把它当成权威结论。**

## 七、作为 AI 技能使用

把整个仓库放进你的 Skill 目录即可：

```bash
# WorkBuddy / Claude Code
git clone <repo> ~/.workbuddy/skills/bazi-fortune

# 或者用软链接指向仓库目录，改代码立刻生效
ln -s "$(pwd)" ~/.workbuddy/skills/bazi-fortune
```

之后可以这样对话：

> 我 1990 年 6 月 15 日下午两点半出生在北京，男，看看我这个八字怎么样？

助手会先问清楚性别与时辰确信度、跑 `scripts/bazi.py` 排盘、再按 `references/`
组织解读。

**技能的部分写在 `SKILL.md` 里**，包括触发词、必须问的信息、
不许越界的红线（不许编造健康/财运预测、不许虚构案例）。

## 八、开源边界：明确不做的事

| 不做 | 原因 |
| --- | --- |
| 吉凶断言、运势打分、宜忌 | 那是解读者的活，不是引擎的活。写进引擎就变成了不可复核的权威口吻 |
| 改运建议、择日、合婚算法 | 同理，且更容易被用来牟利 |
| 农历日期显示 | 八字用干支历。需要农历请自行搭配万年历库，别让本项目长出依赖 |
| 汉服排盘 App、付费接口 | 本项目只做引擎与技能层，UI 是别人的事 |

## 九、致谢与来源

- **四柱期望值交叉校验**：取自该项目
  `scripts/regression/sizhu-lichun-boundary.test.ts` 中的两个用例
  （1990-06-15 午时、2004-02-04 立春前丑时）。两个独立实现得出同一结果，
  是本项目最强的外部验证。
- **天文算法**：Jean Meeus, *Astronomical Algorithms*, 2nd ed., Willmann-Bell, 1998.
- **均时差**：NOAA Solar Calculator 近似式。
- **ΔT**：IERS / Espenak–Meeus 公布值。
- **口诀**：《渊海子平》《三命通会》《滴天髓》《子平真诠》，具体采用哪一家写在 `references/decisions.md`。
